# Linux OS 运行时信息最终采集决策

## 文档定位

本文是 RebootSnap 从完整候选采集项基线中筛选最终采集范围的决策文档。

本文只负责记录哪些 `RT-xx-yy-zz` 三级候选采集项进入最终采集范围、哪些暂缓、哪些禁止采集，以及对应理由。本文不定义具体采集命令、字段 schema、存储格式、报告布局或产品交互。

本文当前固定默认采集约束和首轮采集范围。首轮决策以重启前故障复盘价值、低资源占用、低扰动和有界执行为主要取舍依据；具体采集命令、字段 schema、存储格式和报告布局仍在后续 collector 设计中定义。

## 输入基线

最终采集决策必须从以下稳定入口筛选：

- 一级大类：`docs/linux-runtime-info-categories.md`
- 二级分类：`docs/linux-runtime-info-subcategories.md`
- 三级候选采集项：`docs/linux-runtime-info-collection-items.md`

不得绕过三级候选采集项文档直接新增最终采集项。如果发现三级基线缺项，应先更新 `docs/linux-runtime-info-collection-items.md`，再回到本文决策。

## 默认采集约束

collector 的默认运行场景是假设主机已经不稳定、资源紧张，且重启窗口有限。因此默认采集必须遵守以下约束：

- 只读采集：默认不得写入 OS 状态、改变内核参数、刷新缓存、触发修复、重启服务、加载模块、附着新探针或创建新的长期运行对象。
- 有界执行：每个采集项必须有超时、输出大小上限和失败降级；超时或权限不足时记录不可用原因并继续后续项。
- 低资源占用：优先读取已有的内核、procfs、sysfs、netlink、service manager 或系统守护进程状态；避免递归全盘扫描、全量 payload dump、阻塞式设备探测和可能触发大量 I/O 的遍历。
- 高证据密度：优先保留重启后无法恢复、能直接解释故障现场的身份、状态、队列、计数、错误和引用关系。
- 渐进采集：`必采` 是默认最小证据包；`选采` 只能在能力、权限、剩余时间和资源预算允许时执行；`暂缓` 不进入默认 collector。
- 敏感最小化：默认不采集环境变量值、密钥 payload、认证材料内容、应用业务 payload、普通文件内容或用户隐私数据；如需保留，只能记录存在性、大小、引用关系和敏感标记。
- 不以完整性牺牲稳定性：如果一个信息理论上有价值但采集成本高、可能卡住或对复盘帮助有限，默认不采。

## 决策状态

本文使用以下固定状态：

| 状态 | 含义 |
| --- | --- |
| `必采` | 进入默认 collector 范围；缺失时应在结果中明确记录不可用原因。 |
| `选采` | 可由能力、权限、配置或环境条件启用；默认是否启用需在后续实现策略中定义。 |
| `暂缓` | 分类成立，但当前版本不进入采集范围；必须说明暂缓原因和重新评估条件。 |
| `禁止采集` | 因安全、隐私、破坏性、副作用或边界不匹配，不应由 collector 采集。 |
| `待定` | 框架占位状态；具体决策前不得进入 collector 实现。 |

首轮默认策略补充说明：

- `必采` 表示进入默认最小证据包，但实现仍必须使用超时、大小限制和失败降级。
- `选采` 表示分类成立且有复盘价值，但默认需要能力探测、显式配置、触发条件或剩余预算。
- `暂缓` 表示当前不纳入 collector 默认范围；后续只有在能证明低扰动、可限时和高证据价值时才重新评估。
- `禁止采集` 表示禁止采集内容或动作本身；同一三级项中的非敏感元数据仍可通过其他决策行进入 `必采` 或 `选采`。

## 决策维度

每个最终采集决策必须至少说明：

- `三级项`：引用一个或多个 `RT-xx-yy-zz`。
- `状态`：使用本文固定状态。
- `证据价值`：说明对重启后排障、事实复原或根因分析的价值。
- `采集风险`：说明权限、敏感信息、副作用、性能或稳定性风险。
- `版本范围`：说明目标版本、发行版或内核能力约束；无法确定时写明待验证。
- `验证依据`：引用官方文档、源码依据组、人工审核或测试样本。
- `后续约束`：说明对 collector、脱敏、报告或测试的要求。

## 完整性检查

后续填充具体决策时必须满足：

- 每个被纳入最终决策的 `RT-xx-yy-zz` 必须存在于 `docs/linux-runtime-info-collection-items.md`。
- 每个被标记为 `必采` 或 `选采` 的项目必须说明采集风险和后续约束。
- 每个被标记为 `禁止采集` 的项目必须说明禁止原因。
- 每个保留为 `待定` 的项目不得进入 collector 实现。
- 本文更新时必须同步更新 `CHANGELOG.md`，并运行 `scripts/verify.sh`。
