# 0001 - 固定 Linux OS 运行时信息边界

- **状态**：生效
- **日期**：2026-05-15
- **范围**：`runtime-taxonomy`

## 背景

- RebootSnap 的核心目标是在 Linux 服务器重启前保存 OS 层运行时现场，为重启后排障和根因分析留下系统证据。
- 如果把应用、容器平台、编排平台、虚拟化管理平台或业务系统对象提升为一等对象，后续分类、采集项、数据模型和报告视图会随上层平台漂移，难以保持稳定。
- `docs/linux-runtime-info-categories.md` 和 `docs/linux-runtime-info-subcategories.md` 已经建立大类和二级分类基线，需要用决策记录固定这些文档背后的长期取舍。

## 决策

- RebootSnap 的主要对象固定为当前 Linux 启动实例中的 `Linux OS 运行时信息`，具体边界以 `docs/linux-runtime-info-categories.md` 的核心定义和系统视角边界为准。
- `RT-01` 到 `RT-21` 是稳定上层分类；`RT-xx-yy` 是后续采集项、数据模型和报告视图的优先挂靠点。
- 应用、容器、Pod、VM、数据库实例等上层对象不进入 OS 运行时信息一级分类；它们在 Linux 层的表现应拆回进程、namespace、cgroup、挂载、网络、设备、文件引用、socket 等系统对象。
- 采集命令、字段结构、权限模型、脱敏策略和报告布局不在分类文档中提前固定，后续应在对应实现或设计文档中定义。
- 删除、重命名或重编号稳定分类 ID，或新增一级分类，必须先由人类维护者确认。

## 影响

- 后续新增采集项时，应先判断能否挂靠到现有 `RT-xx-yy` 二级分类；不能绕过现有分类直接创建新的上层对象模型。
- 后续实现可以支持容器、虚拟机或业务系统排障场景，但报告和证据模型仍应以 Linux OS 运行时对象为底座。
- 如果发现官方 Linux OS 运行态中存在无法归入现有分类的新对象，应先提出设计变更和人类确认请求，再修改分类文档、项目地图和变更记录。

## 备选方案

- 采用应用或业务系统视角作为一级分类。未采用，因为这会让 RebootSnap 的核心边界依赖不同运行环境和业务栈，削弱重启前 OS 现场证据的一致性。
- 采用采集命令或文件路径作为分类主轴。未采用，因为命令和路径会随发行版、内核版本和工具实现变化，不适合作为长期设计边界。
- 只保留 21 个大类，不建立二级分类。未采用，因为后续采集项和报告视图需要比大类更细的稳定挂靠点。

## 验证

- 人工核对 `docs/linux-runtime-info-categories.md`、`docs/linux-runtime-info-subcategories.md` 和 `docs/glossary.md` 中的核心定义、排除边界和稳定术语一致。
- 本决策只固定既有设计取舍，不新增采集命令、外部依赖或安全边界。
